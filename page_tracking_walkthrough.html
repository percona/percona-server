Page Tracking in InnoDB — an internal walkthrough

A top-down tour of the page-archive subsystem — what it tracks, where it hooks, how it persists, how it reads back, and the surfaces where things go wrong. Internal-engineering audience. Click Next → at the bottom to navigate.

1. What and why

Page tracking is a side-channel that records which InnoDB pages were modified and when, so a later reader can ask "give me the page‑ids that changed between LSN A and LSN B" and get an exact answer without having to scan every file.

1.1 What it tracks

For every page that flushes from the buffer pool, page tracking writes a small fixed‑size record into a side log. That record is a page‑id — effectively the global identity of the page within the entire InnoDB cluster. Hover the pages below to see what each represents.

A page_id is the pair (tablespace_id, page_no). The tablespace_id picks one of InnoDB's files; the page_no is the slot index within that file. The pink slot is "currently dirty" — the thing page tracking will eventually record once the page cleaner flushes it.

Note that page tracking does NOT capture the contents of the page — only the identity. The actual modified pages live in the data files and in the redo log. Page tracking just maintains a fast "what changed, when" index over them.

1.2 What it's for

Three real consumers in Percona Server today:

  • Incremental backups — the workhorse case. mysqlbackup --incremental and Percona XtraBackup call mysqlbackup_page_track_get_changed_pages(start_lsn, stop_lsn) to learn which pages to copy. Without page tracking the alternative is a full file scan + checksum diff, which is orders of magnitude slower on a large dataset.
  • Clone plugin — uses page tracking as one of its bulk-transfer accelerators so cloning doesn't have to ship every page from scratch.
  • Custom replication / PITR helpers — any tool that wants a fast "what changed since LSN X" index without re-deriving it from the redo log.
What page tracking does NOT do: It does not track DDL operations, undo log changes, or modifications to redo. It does not give you the actual byte changes — only the page‑ids. Reasoning about row-level changes still goes through the redo log or binlog.

1.3 The big picture

At ten thousand feet, the subsystem is a producer/consumer pipeline glued to the buffer pool's flush path:

The buffer pool's page cleaner notices a dirty page (pink), flushes it to the .ibd file, and on the way calls track_page(). The call appends a page-id entry into an in-memory ring of blocks. A background archiver thread drains full (amber) blocks out to disk into a sequence of 32 MB files named ib_page_0, ib_page_1, …

The rest of this walkthrough zooms in, top to bottom: how the hook fires, how the ring works, how a block ends up on disk, what's inside a file, how the in-memory bookkeeping is rebuilt at restart, and finally how a SELECT reads through all of it to answer "what changed between LSN A and LSN B".

2. Where tracking hooks into InnoDB

2.1 The hook point

There is exactly one place in InnoDB where a page change becomes durably visible to anything outside the buffer pool: a page cleaner thread (occasionally a user thread doing a forced flush) writing a dirty page to its data file. Page tracking puts its hook right there. Inside buf_flush_write_block_low() — the lowest-level routine that emits a page write — the call to track_page() happens synchronously on the same thread.

The hook is synchronous and runs on the page cleaner thread (or whatever thread is performing the flush). It's cheap: a short critical section under a mutex, a 6-byte write into the active in-memory block, possibly a state flip to mark the block "ready to flush", and return.

2.2 Why flush, not modification

A page can be modified many times while sitting in the buffer pool — perhaps thousands of UPDATEs touch the same row over the course of seconds. If page tracking fired at modification time, every one of those would produce a record. The flush is the natural deduplication point: no matter how many in-pool modifications a page receives, only one flush eventually carries them to disk, and that flush emits exactly one page-id into the archive.

The trade-off: page tracking is "behind" the buffer pool by however long pages sit dirty before being flushed. That's fine, because the consumer (incremental backup) doesn't care that a page changed at LSN X; it cares that the page changed at some point in the requested LSN range and therefore needs copying. The flush always happens before the corresponding redo is cleaned out, so by the time a checkpoint LSN advances past a modification, the page either has been flushed (and tracked) or will be tracked imminently.

2.3 What about pages dirtied but never flushed?

If the server crashes before a dirty page reaches disk, no track_page call ever fires for it — the page-id never enters the archive. That's safe by construction: the modification is also not in the data file, so recovery will redo it from the redo log on restart. The first time the recovered (and now in-pool) version of the page gets flushed, the call to track_page fires normally. From the archive's perspective the gap is invisible.

Subtlety: Because the hook fires at flush time, the LSN you'd associate with a page-id (if you were storing one per entry, which we are not) would be the page's flush LSN, not its modification LSN. The system finesses this by stamping LSN markers on the enclosing block (see Section 8 later in the walkthrough) rather than on individual entries.

3. The in-memory pipeline

3.1 The ring of blocks

Page-id entries don't go straight to disk. They accumulate in a small ring of fixed-size buffers called blocks. Each block is exactly the same size as the on-disk block (16,384 bytes — see Section 7), so when one fills up it can be flushed verbatim, no marshalling required. Each block carries a state; the ring rotates as the page cleaner appends entries and the archiver drains full blocks. Click Tick → below to walk through the cycle.

tick 0 -- start; slot 0 becomes ACTIVE
The ring really wraps — after slot 6 the producer comes back to slot 0 to reuse it. Drawn linearly so transitions are easy to follow. Step through and watch the producer (orange marker) march forward while the consumer (the next block out, which goes blue then grey) chases behind.

3.2 Producer and consumer

The producer (the page cleaner thread holding the flush latch) runs the loop: 

track_page(space, page_no):
    acquire(arch_oper_mutex)
    active = m_data.get_block(&m_write_pos, ARCH_DATA_BLOCK)
    if active is full:
        mark active as READY_TO_FLUSH
        advance m_write_pos to the next slot, mark it ACTIVE
        active = the new block
    active.append((space, page_no))
    release(arch_oper_mutex)

The archiver thread is the consumer. It sleeps on a condition variable, wakes when any block becomes READY_TO_FLUSH (or when a checkpoint forces a flush of the active block), drains every ready block to disk, and marks them FLUSHED so the slot can be reused.

3.3 What triggers a flush of the active block

Two distinct flavours of flush, only one of which actually seals the block:

  1. Block fills up — SEALING flush. When the active block has no more room for a page-id entry, the page cleaner marks it READY_TO_FLUSH and rolls m_write_pos to the next slot. The next slot becomes ACTIVE. The previous block is now sealed at data_len = 16352 and goes through BEING_FLUSHED → FLUSHED. This is the only path that seals a block at full data_len.
  2. InnoDB checkpoint — PARTIAL flush. flush_at_checkpoint(checkpoint_lsn) updates the active block's header with the new stop_lsn (= the new checkpoint_lsn, see Section 8) and asks the archiver to write the current state to disk. The block stays ACTIVE. m_write_pos doesn't move. The next track_page continues appending into the same block, and the next partial flush overwrites the on-disk image with a slightly larger data_len.
  3. mysqlbackup_page_track_set(1) — also a PARTIAL flush. A backup tool's explicit save-reset request triggers the same partial-flush mechanism as a checkpoint, so the new reset entry is durable on disk before the call returns. Same property: block stays ACTIVE, no sealing.
Consequence: the only way a sealed block on disk can have data_len < 16352 is via artificial test knobs (e.g., innodb_arch_page_test_max_entries=1). In normal operation — no matter how many checkpoints fire or how often set(1) is called — sealed data blocks always have data_len = 16352. The only partial block at any moment is the active one.

There is no time-based flush. As long as nothing is appending to the active block AND no checkpoint fires AND no set(1) fires, the block can sit unflushed indefinitely.

4. Threads and their dance

Five distinct threads touch the page-archive state machine at runtime. They communicate through three short-held mutexes and a small handful of shared in-memory fields. Knowing who is allowed to do what is the difference between "this code is safe" and "this code has a race".

4.1 The roster

The page cleaner is the only thread that ever calls track_page(). The archiver is the only one that writes the on-disk files. The checkpoint thread doesn't write blocks itself — it just stamps stop_lsn onto whatever block is currently active and asks the archiver to flush. SELECT-side reads are isolated: they touch the in-memory ring (under m_oper_mutex) and on-disk files separately.

4.2 The three mutexes

MutexProtectsHeld byHeld for
m_oper_mutex active block pointer (m_write_pos), ring slot states, m_latest_stop_lsn page cleaner during track_page; checkpoint during flush_at_checkpoint; SELECT while reading from the ring microseconds — just long enough to bump a counter or flip a state
m_mutex system-level state (m_state, m_current_group, m_reset list) SELECT during find_reset_point; page_track_set during start/stop milliseconds — binary search across reset points

Lock ordering is documented but tight: m_mutex » m_arch_mutex » m_oper_mutex. Inverting the order in any callsite is the path to a deadlock between the page cleaner and the archiver.

5. Persistence: in-memory → disk

5.1 The doublewrite buffer

Page archive flushes go through a doublewrite file before landing in the final ib_page_F location, for the same reason InnoDB's main doublewrite exists: protection against torn writes. A partial 16-KiB write to ib_page_F would leave that block neither old nor new but half-of-each, which the recovery parser can't tell apart from a valid block.

fsync() both files. block is now durable. if the server crashes between step 2 and step 3, recovery replays from the dblwr copy.
For every flush of an archive block, the archiver writes a copy to the appropriate slot in the page-archive doublewrite file first, then to the final ib_page_F location, then fsyncs both. If a crash interrupts the second write, recovery's validate_and_fill_blocks takes the dblwr copy and finishes the job. The dblwr is just three 16-KiB slots: one for full-block flush, one for partial-block flush, one for the reset block flush — tiny.

5.2 Partial vs full flush

Two flush flavours, two different dblwr slots, two different on-disk write patterns:

  • Full-block flush. The block is sealed (data_len = 16352) and won't change again. Archiver writes the full 16 KiB to dblwr slot 1, then to ib_page_F at the next free slot, then fsyncs.
  • Partial-block flush. A set(1) or checkpoint asked for the active block's state to be made durable, but the block isn't full yet. Archiver writes to dblwr slot 2, then to ib_page_F at the same offset as before (overwriting the previous partial-image), then fsyncs. The same block can go through many partial flushes in its lifetime; each one updates the on-disk image with a slightly larger data_len and a slightly updated stop_lsn in the header.

6. On-disk layout

The on-disk archive lives entirely under #ib_archive/ inside the data directory. Everything we've been discussing so far is just a few file types under that one tree.

active = currently-being-written group, durable = persisted-ok flag. files: 0-byte markers; ib_page_K = 33,488,896 bytes each when full page_group_<begin_lsn_2>/ active durable ib_page_0 ib_page_1 a new group every time set(0) + set(1) resets the archive doublewrite files #ib_16384_0.dblwr #ib_16384_1.dblwr crash-safety scratchpad 3 slots each, 48 KiB total
Each page_group_<lsn> directory is one self-contained tracking epoch: it has its own files numbered from ib_page_0 upward, and its own active + durable marker files. A new group is created the next time tracking is started after being fully stopped. Within a group, the highest-indexed file is the active partial file; everything else is sealed.

6.1 File size arithmetic

A full ib_page_F contains:

  • 1 reset block at slot 0 (16,384 bytes)
  • 2,043 data blocks at slots 1 .. 2043 (each 16,384 bytes)
  • Total: 2,044 × 16,384 = 33,488,896 bytes (32 MiB minus a hair)

The active file is always partial — its size grows in 16 KiB increments each time a block is sealed and a new block is started. So when you see ib_page_180 at exactly 6,766,592 bytes on disk, that's 6,766,592 / 16,384 = 413 slots in use, with the 413th slot being the writer's current active block.

7. Block anatomy

7.1 Header layout

Every block on disk — whether reset block or data block — begins with the same 32-byte header. All multi-byte fields are big-endian.

The header is identical for all block types; type at byte 1 disambiguates. CRC32C covers only the payload bytes — the header itself isn't checksummed. The block_num at bytes 24–31 is stored as a full 64-bit integer here, in the data block; reset entries inside the reset block's payload (right-hand box) reference that block_num with only a 2-byte field, which is the asymmetry called out below.

7.2 The asymmetry between block_num fields

Crucial detail: a data block's own header carries block_num as 8 bytes. But a reset entry inside a reset block stores the reference to that block_num as 2 bytes. So when the writer's real block_num exceeds 65,535, the data blocks themselves remain correct (their u64 block_num in bytes 24-31 holds the full value), but every reset entry that points at one of them loses the high bits.

8. All the LSNs: who writes what, who reads what

The walkthrough has already used the word "LSN" in five different shades. Time to step back: there are four distinct LSN values in play in this subsystem, and the asymmetric way they're used is exactly what makes page tracking correct — provided it's used together with the redo log.

8.1 The four canonical LSN values

current_lsn

checkpoint_lsn InnoDB checkpoint pipeline The most recent LSN past which InnoDB has guaranteed every dirty page modified at an LSN < checkpoint_lsn has been flushed to its data file. Lags current_lsn by the in-flight redo gap.

8.2 The asymmetry: reset_lsn from current_lsn, stop_lsn from checkpoint_lsn

fieldderived fromstamped whensemantic role
reset_lsn current_lsn (the system's "now") at block open; again when mysqlbackup_page_track_set(1) bumps the epoch on the active block start marker. "Tracking epoch began at this LSN."
stop_lsn checkpoint_lsn (the most-recent flush-completion guarantee) at each InnoDB checkpoint, while the block is the active block (overwritten each time) completeness guarantee. "Every page modified up to this LSN has been tracked into the archive."

Why isn't stop_lsn also current_lsn? Because the two LSN values solve fundamentally different problems:

  • A start marker doesn't need a "before" guarantee. When the user starts a new tracking epoch, they just want an LSN they can later use as begin_lsn in a backup query. current_lsn is the strictly-correct "now" value — nothing earlier could possibly need to be tracked under this epoch by definition.
  • A completeness guarantee can only come from a checkpoint. Page tracking emits a page-id when the page flushes. So at any moment, the LSN range [checkpoint_lsn, current_lsn] contains modifications that are in the redo log but whose pages haven't been flushed yet. Those modifications are not in the archive. Stamping stop_lsn = current_lsn would lie: the SELECT walker would terminate thinking it had seen all changes up to current_lsn, but some pages modified just below current_lsn are still dirty in the buffer pool with no archive entry. The next safest LSN for that claim is checkpoint_lsn — the highest LSN where the flush-completion contract holds.

8.3 Visualising the gap

get_changed_pages(start_lsn, stop_lsn) query lives entirely inside the green band: start_lsn ≥ some past reset_lsn, stop_lsn ≤ some past checkpoint_lsn
The "tracked range" is bounded below by some past reset_lsn and above by some past checkpoint_lsn. Anything above the most recent checkpoint_lsn is in the gap — modifications that exist in the redo log but whose pages haven't been flushed yet. The page archive doesn't know about them. That's not a bug; it's the design.

8.4 Why page tracking cannot stand alone

Because the gap exists, page tracking by itself is never enough to reconstruct a database's state at current_lsn. Any complete incremental backup needs both the page archive and the redo log:

  1. Page tracking answers: "which pages changed in the LSN range [start_lsn, checkpoint_lsn]?" That tells the backup tool which pages to read from the .ibd files.
  2. Redo log answers: "what changes happened in the LSN range [checkpoint_lsn, current_lsn] that aren't reflected in the pages on disk yet?" The backup tool replays those records forward so the backup's pages reflect the desired final LSN.

This is why mysqlbackup --incremental and Percona XtraBackup always copy redo log files in addition to the changed pages: the page-track info is the index of where to look; the redo is what fills in the recent-modifications gap. Without the redo, the incremental backup would reflect the state at checkpoint_lsn, not at the time the backup was actually taken.

8.5 Block-header timeline (recap)

The same picture, focused on how a single archive block's reset_lsn and stop_lsn evolve over the block's lifetime:

block_num is stamped at open and frozen. reset_lsn is the value of current_lsn at the time the block was started, and may be re-stamped to a new current_lsn if set(1) fires while this is still the active block. stop_lsn is the value of the most-recent checkpoint_lsn, overwritten at every checkpoint, and finally frozen at whatever checkpoint_lsn was stamped just before the block was sealed.

9. Reset blocks and reset points

A reset point is the on-disk record that says "at this LSN, a new tracking epoch began here". A reset block is the place those records live — slot 0 of every ib_page_F.

9.1 What's stored, and what's missing

Each reset entry on disk is just 4 bytes: 

+-----------------+-----------------+
| block_num (u16) | offset    (u16) |   <- 4 bytes per entry
+-----------------+-----------------+

Notice what's not there: the LSN of the reset itself. The reset block's header has a single file_reset_lsn at the start of the payload, but individual entries don't repeat it.

9.2 The fetch_reset_lsn round-trip

When recovery rebuilds the in-memory reset-point list it needs the full triple (reset_lsn, block_num, offset) for every entry. It already has block_num and offset from the disk record — the missing reset_lsn is recovered by reading the data block at (block_num, offset) and pulling reset_lsn out of its 32-byte header (bytes 16..23). That's the Arch_File_Ctx::fetch_reset_lsn() call we keep referring to.

The reset entry stores (block_num, offset) only. To complete the triple, recovery reads the block at that on-disk position and lifts the reset_lsn field out of its header.

9.3 Why store reset_lsn per-block instead of per-entry?

Three reasons:

  1. Space. An 8-byte LSN per entry would inflate the reset block by 200%. Reset blocks are 16 KiB and entries are 4 bytes today, so a reset block can hold ~4,000 entries.
  2. Redundancy. The data block at (block_num, offset) already carries the reset_lsn that was current when the block was opened. Storing it again would just be duplication.
  3. Self-describing data blocks. Every data block on disk knows which epoch it belongs to, without needing to consult the reset block. Useful for crash-recovery sanity checks.

The price of (2) and (3) is the round-trip read. The price of (1) is the 2-byte block_num field in the entry — which silently wraps once the writer's real block_num crosses 65,535. The architectural trade-off between entry compactness and value range is the seed of one of the bugs we'll cover next.

10. Reading: the SELECT path

The end-to-end path that runs when an incremental backup or clone tool calls mysqlbackup_page_track_get_changed_pages(start_lsn, stop_lsn):

The whole SELECT path is just (1) find the right reset point via binary search, (2) open the file at the implied slot, (3) walk forward block-by-block until you've covered the requested LSN range. No clever indexing; the linear walk is what makes this scheme cheap to write but acceptable to read — the archive is tiny compared to the data files.

10.1 Performance note

For a typical incremental backup the walk covers a handful of files. A full archive is ~33 MB per file, ~2,725 page-id entries per block, ~5.5 million entries per file. The walker is sequential reads, so reading even a 100-file range (3 GiB of archive) is much cheaper than scanning the actual tablespaces (potentially TiB) to figure out the same set of pages by checksum diff.

11. Startup and recovery

At server start, the page-tracking subsystem has to rebuild everything in memory from what's on disk: which groups exist, which file is active, where the writer was, and the full list of reset points. The entry point is Arch_Page_Sys::recover().

Recovery is essentially "rebuild the in-memory state from the on-disk files." Each step has one job. scan_for_groups discovers what's there. cleanup_if_required drops tail files that weren't fully written. replace_pages_from_dblwr uses the doublewrite to repair any torn writes. parse_reset_points rebuilds the m_reset list per file by calling fetch_reset_lsn on each entry.

11.1 An invariant worth highlighting

fetch_reset_lsn doesn't read from the implied file (the one persisted_bn / 2043 would naively point to). It reads from the same file the reset entry was found in (call it the reset_point file). The justification is an invariant: a writer can only save a reset point in the file it's actively writing, so in normal operation the reset entry's implied file is the reset_point file. Keep this invariant in mind — we'll see what happens when it gets broken in the next section.

12. Putting it together

A complete end-to-end walk — from one user UPDATE through to the incremental backup that consumes its page-id.

  1. t0 — user thread: UPDATE t SET ... dirties a page in the buffer pool. Redo logs the change. No page-tracking action yet.
  2. t1 — page cleaner thread: picks the dirty page, calls buf_flush_write_block_low() which inline-calls track_page(space=5, page_no=421). The tracker appends a 6-byte entry into the active in-memory block and returns. Cleaner finishes the write to the .ibd file.
  3. t2 — checkpoint thread: a periodic checkpoint fires, stamps stop_lsn = L on the active block, asks the archiver to flush.
  4. t3 — archiver thread: drains the now-READY_TO_FLUSH block, writes it to #ib_16384_0.dblwr first, then to ib_page_180 at slot 412, fsyncs both. Block transitions to FLUSHED.
  5. t4 — user runs mysqlbackup --incremental --start-lsn=L0 --stop-lsn=L1. mysqlbackup calls mysqlbackup_page_track_get_changed_pages(L0, L1) via UDF.
  6. t5 — SELECT thread: find_reset_point(L0) binary-searches m_reset, returns the entry whose reset_lsn is the largest ≤ L0. Returns (block_num B, offset O).
  7. t6 — SELECT thread: opens ib_page_F where F = B / 2043, reads at slot (B % 2043) + 1. Reads block header, gets data_len, accumulates page-ids from offset O onward. Advances to next slot, repeats.
  8. t7 — SELECT thread: reaches a block whose stop_lsn > L1. Terminates the walk. Returns the accumulated page-id set to mysqlbackup.
  9. t8 — mysqlbackup copies the actual pages identified by step t7 out of the .ibd files.
  10. t9 — mysqlbackup also copies the redo log from checkpoint_lsn forward. Page tracking covered the LSN range [start_lsn, checkpoint_lsn]; the redo covers the gap up to current_lsn (see Section 8.4). On restore, the copied pages get redo-replayed up to the target LSN. Incremental backup done.

That's the whole story. Every component the rest of the walkthrough discussed has its specific moment in this sequence — including the redo log, which page tracking always needs as a companion to fill in the recent-modifications gap.

13. Bug: truncated reset-entry block_num

The first bug exploits the 2-byte block_num field inside reset entries (Section 7, Section 9). Once the writer crosses file 31 — i.e., the writer's real block_num ≥ 65,536 — mach_write_to_2 silently chops the high bits when persisting a reset entry. Try it yourself below.

13.1 The truncation, visualised

A real block_num is 8 bytes (u64). The on-disk reset-entry field is 2 bytes (u16). mach_write_to_2 writes only the low 16 bits and discards the rest. The high 48 bits never reach the disk and cannot be recovered from the entry alone.

For any real block_num < 65,536, the 6 dropped bytes are all zero and nothing is lost. For any block_num ≥ 65,536 (i.e., the writer is in ib_page_32 or higher), at least one of the dropped bytes is non-zero and the on-disk value no longer matches reality.

13.2 Interactive: try a real block_num

Type any real block_num and see what gets persisted into the reset entry, what file the truncated value implies, and what file it should have implied.

Important: The truncation affects only the reset entry's 2-byte block_num field (see Section 7.2). A data block's own header still carries the full 8-byte block_num at bytes 24–31 — the data blocks themselves remain correct. The simulator below shows the value as it lives inside a reset entry, not what's stored in any data block header.
try 5000 (no truncation) / 65535 (max value 2 bytes can hold, still fits cleanly) / 65536 (FIRST value that wraps -- persisted becomes 0) / 67419 (start of ib_page_33) / 368151 (customer case)

13.3 Three faces of the same bug

The truncated entry sits harmless on disk until something tries to use it. What happens next depends entirely on the state of the archive at use time:

Three different runtime conditions, three different observable behaviours. The first two are loud (the server stops). The third is quiet (the server is fine; the backup just isn't). Across customer reports, B is the most common; C is the most dangerous.

13.4 How users experience it

  • Outage class. Server fails to start after a planned restart. Worst case, the operator forces a recovery by removing #ib_archive/page_group_*, losing all tracking history. The instance comes back but the next incremental backup has to be a full backup.
  • Backup class. Backup tools crash the server mid-backup. Either the same operator workaround applies, or the backup is abandoned and a full backup runs instead.
  • Restore class (worst). Backups appear to succeed for weeks. The corruption is only discovered during an actual restore attempt — usually the worst possible moment.

14. Bug: m_count off-by-N after purge

The second bug is at the seam between purge and recovery. After mysqlbackup_page_track_purge_up_to() removes the oldest archive files, the on-disk range now starts at a non-zero index. Recovery initialises the writer's "next file index" counter wrong — and the next archive flush overwrites a live file in place.

14.1 Walk through the state, step by step

Use Step → to advance through what happens. Each step shows the on-disk layout and the writer's internal m_count bookkeeping.

step 0 -- starting state
The stepper walks through one full cycle — initial workload → purge → restart → recovery's bookkeeping → the writer's next file open. Watch m_count and the "next flush opens file_index" together; when they disagree with the actual on-disk state of the file at that index, that's the bug.

14.2 What's actually happening

Recovery calls Arch_File_Ctx::init(num_files) where num_files is the count of files in the group (e.g., 5 after purging the first 3). That function does: 

m_count = num_files;            // sets the "next file index to allocate"

… which is wrong when the group's lowest file index is non-zero. The correct expression is m_count = start_index + num_files. After purge of the first 3, surviving files are at indices [3..7] (5 files), and the next file should be ib_page_8 — not ib_page_5.

14.3 How users experience it

  • Silent corruption of a live archive file. The overwrite is in-place, no error, no log. Reset entries that lived in that file are gone; subsequent data blocks claim a wrong block_num.
  • Backups derived from the corrupted archive are silently wrong. The same restore-time discovery problem as Bug 1's face C.
  • On the next restart, recovery may emit MY-013581 "Page archiver system's recovery failed" if scan_for_groups notices the inconsistency — in which case page tracking is disabled for that boot, the server itself comes up.
  • Always paired with Bug 1 in practice. The customer hits Bug 1 first, removes the archive directory, restarts. Page tracking starts a new group from scratch. The next purge+restart cycle hits this bug. So in the wild they show up as a chain.

15. Bug: page cleaner / archiver deadlock

The third bug is a classic lock-ordering inversion between two of the threads we met in Section 4. Under sustained heavy tracking load it can produce a hung shutdown.

15.1 The correct lock order

Section 4.2 listed three mutexes. The whole subsystem stays safe iff every call site takes them in the documented order:

15.2 Walk the deadlock formation

Two threads, two mutexes, taken in conflicting orders. Step through to watch the cycle form.

step 0 -- both threads idle
The page cleaner takes m_oper_mutex first, then tries m_arch_mutex — that order is fine. The archiver takes m_arch_mutex first, then tries m_oper_mutex — that's the inversion. When both happen concurrently, each thread holds the lock the other one needs.

15.3 How users experience it

  • Hung shutdown. SHUTDOWN or systemctl stop never returns. The shutdown is waiting for the page cleaner to finish; the page cleaner is waiting on m_oper_mutex; the archiver holds it.
  • Stack traces show the cycle directly. gdb thread apply all bt on the hung mysqld shows page cleaner blocked on the operation mutex, archiver blocked on the operation mutex, no progress anywhere.
  • Only recourse is SIGKILL. The forced kill triggers crash recovery on the next start, but recovery itself works fine — this is not a corruption bug, just a liveness bug.
  • Fixed in current branch. The patched code reorders the locks consistently and the deadlock no longer forms. Only relevant to un-patched builds (anything before the fix landed).

16. The verification tool

verify_page_archive.py in the repo runs against a copy of an archive directory and reports which (if any) of the three failure modes the dump exhibits. It's read-only; it never modifies the archive, so it's safe to point at a customer dump for triage.

16.1 What it checks

  • Reset entries with truncated block_num (Bug 1 surface). For each suspect entry it prints a per-entry table with the field reference legend — reset_point.block_num, real_block_num, reset_point.offset, the landing block's data_len, the SELECT-side underflow check, and the recovery-side past-EOF check.
  • Data blocks whose block_num doesn't match the file they live in (Bug 2 fingerprint).
  • Files that aren't full (33,488,896 bytes). The active tail is expected to be partial; anything else is suspicious.
  • Zeroed reset blocks correlated with wrong-block_num data blocks (the exact "writer reopened an existing file" signature of Bug 2).
  • Gaps and duplicates in the on-disk block_num sequence across files.
  • CRC32C checksum mismatches (only if the crc32c Python package is available).

16.2 Output

A per-group report ending in a final-verdict banner: 

ARCHIVE IS UNUSABLE -- SERVER WILL NOT START
  N reset entry(s) point at a position past the reset_point file's
  actual size. ... EVERY restart attempt will die the same way.
  The page-archive directory must be removed or the affected file
  truncated/repaired before the server can start.

or a green-light variant: 

OK: no symptoms detected. Archive looks healthy.

16.3 Running it

python3 verify_page_archive.py /path/to/copy_of_ib_archive

For Bug 1's silent-wrong-data case (face C above), the script flags the truncated entries but won't tell you which specific incremental backups happened to use them. Once flagged, the safe assumption is that all increments taken after the first truncated entry was created are suspect.
