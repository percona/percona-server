PS-11175 — how a truncated block number crashes the backup

A 10-step walkthrough: from a 2-byte truncation on disk to MY-012642 — Tried to read 16777216 bytes at offset 3414897408. Use ← → or the buttons.
1

3

What a block holds — reset_lsn vs stop_lsn

Every block starts with a fixed header, then the payload (page-IDs for data blocks). Two LSNs in the header matter:

block_numthis block's global number
data_lenbytes of payload
reset_lsnthe reset era this block belongs to — the LSN of the most recent set(1). Step function: constant within an era, jumps up at each reset.
stop_lsnhighest redo LSN whose page changes are captured in this block. Monotonic — every later block has a larger stop_lsn. Derived from the redo LSN at flush time.
slot 0 — RESET BLOCK
file_lsn = LSN of the file's first reset point
+ list of reset points: {block_num, offset}
Why stop_lsn? A get_changed_pages(start,stop) walk needs to know, per block, “does this block still contain changes ≤ stop?” — so it reads each block header's stop_lsn to decide where to stop. reset_lsn, by contrast, identifies which set(1) a block belongs to.
4

User runs set(1) — what lands on disk

A set(1) reset at LSN 9,000,000 while the write cursor is at block 67450 (ib_page_33, slot 31). Arch_Block::add_reset appends a reset entry to slot 0 — and writes block_num with mach_write_to_2 (only 2 bytes):

// real block_num = 67450
mach_write_to_8(buf, 9000000);                 // file_lsn (8 bytes)
mach_write_to_2(buf+len, 67450);            // 67450 needs 17 bits -> TRUNCATED
mach_write_to_2(buf+len, 64);                  // offset (fits)

   67450 = 0x0001_07BA   → low 2 bytes only → 0x07BA = 1914
ib_page_33 · slot 0 (reset block) on disk
file_lsn = 9,000,000  |  entry → { block_num = 1914 , offset = 64 }  (was 67450!)
The on-disk reset entry now says block 1914, but the real reset was at block 67450. The high bits are gone forever.
5

Everything is fine — until a restart

In memory, save_reset_point_in_mem stored the full, correct 67450. Live reads use this in-memory copy, so backups work perfectly. The corruption sits silently on disk.

in memory (m_reset)
block_num = 67450 ✓
vs
on disk (ib_page_33 reset block)
block_num = 1914 ✗
DORMANT. The bug only arms when memory is thrown away and m_reset must be rebuilt from the disk bytes — i.e. on the next restart. (Customers always saw the crash after a restart.)
6

Restart — recovery re-discovers the reset points

On startup, parse_reset_points walks each file's reset block and rebuilds m_reset. For our entry it reads back the truncated 1914 and then asks fetch_reset_lsn for that block's reset era:

reset_file.m_lsn = mach_read_from_8(buf);      // = 9,000,000  (file_lsn)
pos.m_block_num  = mach_read_from_2(buf);      // = 1914  (truncated)
pos.m_offset     = mach_read_from_2(buf);      // = 64
start_point.lsn  = fetch_reset_lsn(1914);       // reads a block's reset_lsn header
So the rebuilt reset point gets its LSN from fetch_reset_lsn(1914) — and that is where it all goes wrong. Step 7 shows exactly which block gets read.
7

The key trap — 1914 is read from the current file, not where it “belongs”

The value 1914 is interpreted two different ways. fetch_reset_lsn uses only the within-file offset, reading from the file it already has open (ib_page_33) — it never opens the file the number maps to:

8

In memory — the broken vector and the out-of-bounds read

The rebuilt entry now violates the invariant m_lsn == start_point[0].lsn:

m_reset entry (BROKEN)
m_lsn = 9,000,000
start_point[0].lsn = 9,800,000  (> m_lsn!)
start_point[0].pos = {blk 1914, off 64}

A lookup for an LSN in the gap (e.g. 9,100,000) makes std::lower_bound return begin(), and the unguarded --begin() reads the Arch_Point before the buffer:

P − 24 (heap)
GARBAGE
▲ --begin() lands here
P = begin()
lsn = 9,800,000
pos = {1914,64}
reset_point_it = lower_bound(lsn >= 9,100,000);   // 9,800,000 >= 9,100,000 -> returns begin()
if (it==end() || it->lsn != check) {
    ut_ad(it != begin());   // DEBUG asserts | RELEASE no-op
    --it;                  // --begin() -> reads BEFORE the buffer
}
reset_point = *it;         // = GARBAGE { block_num, m_offset }
Because the vector is non-empty (it has capacity), this is a garbage read, not a crash. The bytes happen to give e.g. block_num = 1, m_offset = 3,414,897,408 (~3.18 GB).
9

Later, a backup SELECT picks up the garbage

xtrabackup runs SELECT … get_changed_pages(9,100,000, …). It calls find_reset_point, which returns that garbage position as the place to start reading:

success = group->find_reset_point(9100000, reset_point);
start_pos = reset_point.pos;   // { block_num = 1 , m_offset = 3,414,897,408 }
start_pos.block_num
1 → get_file_index → ib_page_1
start_pos.m_offset
3,414,897,408
A sane-low block_num sends the read to a real low file (ib_page_1); the garbage m_offset is the ~3.18 GB that will blow past the end of that 32 MB file.
10

The 16 MB read at a 3.18 GB offset → crash

In the read loop, bytes_left underflows (unsigned), so the read length is clamped to the 16 MB buffer; then the offset is built from the garbage:

bytes_left = data_len + 32;          // small, e.g. 16384
bytes_left -= cur_pos.m_offset;      // 16384 - 3.4e9  -> UNSIGNED UNDERFLOW -> ~4 GB
read_len = min(bytes_left, buf_len); // clamped -> 16777216 (16 MB)

file_index = get_file_index(1);      // -> ib_page_1
offset = get_file_offset(1) + 3414897408;   // ~3.18 GB
os_file_read(... read_len=16 MB, offset);   // past EOF -> reads 0
ib_page_1 (32 MB)
read 16 MB @ 3.18 GB
0 ───────────── 32 MB ·······························▶ 3.18 GB (way past EOF)
[ERROR] [MY-012642] [InnoDB] Tried to read 16777216 bytes at offset 3414897408,
        but was only able to read 0 of FD 17282, filename .../ib_page_1
[MY-012646] 'read' returned OS error 122
That is the customer crash. Two fixes: (1) add_reset must store block_num without truncation (or reject ≥ 2¹⁶); (2) find_reset_point must guard if (reset_point_it == begin()) return false; so a corrupt/unsorted reset vector can never read before the buffer.
